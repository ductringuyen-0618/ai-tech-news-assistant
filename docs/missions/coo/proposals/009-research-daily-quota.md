# Research Daily Quota

## What you get
The Research tab now tells you plainly how many free research runs you have left today ("3 of 5 used · resets at midnight UTC") instead of staying silent until something breaks. Once the day's five are used, the button disables with an honest "come back tomorrow for 5 more" message instead of a cryptic "another run is in flight" error. Nothing about the research itself changes — this only makes the existing limit visible and gives everyone a reason to open the app again the next day.

## Why start this now
Right now the only cap on Research is a single global "one run at a time" lock with no per-visitor framing — a reviewer poking at the product sees either nothing or a confusing error, never a deliberate limit. A past review round flagged this exact gap as the single most credible signal that the builder understands unit economics (LLM calls cost money), and nothing shipped since has touched it. It also doubles as a lightweight retention hook: a quota that visibly refills every 24 hours gives people an honest reason to come back the next day, the same mechanic that makes daily-limit products sticky — at a cost of a small, self-contained backend change plus a status readout on a page that already exists.

## Problem / opportunity
`POST /api/research` already has a process-wide single-in-flight gate (`backend/src/api/routes/research.py`), but it's purely a concurrency guard, not a per-visitor limit — one person can run research back-to-back all day, and the only feedback anyone gets is a raw `429` with no explanation. The app already has a stable anonymous identity (`X-Client-Id`, generated by `frontend/src/lib/clientId.ts` and already read by the settings route) that a per-visitor quota can key on, but nothing uses it for Research today.

## Proposed solution
- **Backend** (`backend/src/api/routes/research.py`): add a small per-`client_id`, per-UTC-day counter (in-memory dict, same scale as the existing `_in_flight` lock — single process, no new infra) capped at 5 runs/day. `POST /api/research` reads the `X-Client-Id` header (same `Header(default=None, alias="X-Client-Id")` pattern already used in `settings.py`), increments the counter on a successful dispatch, and returns `429` with a distinct, honest message (`"Daily research limit reached (5/5). Resets at 00:00 UTC."`) when exhausted — kept separate from the existing "another run is in flight" 429 so the frontend can tell the two apart. Add `GET /api/research/quota` returning `{"used": int, "limit": 5, "resets_at": "<ISO timestamp>"}` for the same `client_id` so the frontend can show the count without spending a run.
- **Frontend** (`frontend/src/components/ResearchMode.tsx`): on mount, fetch `/api/research/quota` and render a small mono status line near the query input ("3 of 5 used today · resets 00:00 UTC"), updated after each run. When the quota-exceeded 429 is hit, show the friendly "come back tomorrow" copy in the existing `research-error-panel` instead of the raw backend string, and disable the submit control until the quota resets.
- No new dependency, no new database table, no secret — the counter is in-memory like the existing in-flight gate, and resets naturally at midnight (and on redeploy, which is an acceptable soft limit, not a billing control).

## Effort estimate
S/M — one new counter plus one new read-only endpoint on a route that already exists, and one status readout plus one friendlier error branch on a page that already exists. No schema change, no new service.

## Validation contract
- Functional assertions:
  - `GET /api/research/quota` returns `used`/`limit`/`resets_at` for the calling `client_id`, starting at `used: 0` for a never-seen client.
  - `POST /api/research` increments that client's counter on each accepted run and returns the quota-exceeded `429` (distinct detail string from the in-flight `429`) once 5 runs have been used for the current UTC day.
  - The counter resets for a new UTC day (verified by mocking/advancing the date in a test, not a real 24h wait).
  - A request with no `X-Client-Id` header still works (treated as its own anonymous bucket, matching the existing settings-route fallback behavior) rather than erroring.
- Behavioral assertions:
  - The Research tab shows the live "N of 5 used" status on load and after every run, without the user needing to refresh.
  - Hitting the daily limit disables the submit control and shows the friendly reset-time copy, not a raw backend error string.
  - The existing "another run is in flight" 429 path is untouched and still shows its own message — the two 429 cases must not collide.
- Negative assertions (should NOT happen):
  - No new dependency added to `backend/requirements.txt` or `frontend/package.json`.
  - No new database table/migration.
  - The quota counter is never exposed or settable from the frontend (read-only `GET`, no way to reset it from the client).
- Test commands the build will need to pass:
  - Backend, from `backend/`: `ruff check .`, `mypy . --ignore-missing-imports`, `python -m pytest test_ci.py -v`
  - Frontend, from `frontend/`: `npm run lint`, `npx prettier --check "src/**/*.{js,jsx,ts,tsx,json,css,md}"`, `npx tsc --noEmit`, `npm run build`

## Risks / open questions
- The counter is per-process and in-memory, so a Fly.io redeploy silently resets everyone's quota early — acceptable for a soft, honest-signal limit, but worth saying explicitly in the UI copy ("today" rather than implying a hard guarantee) so it never reads as a broken promise.
- Five runs/day is a guess at a number that feels generous but still real; easy to tune in one place if it turns out too tight or too loose once it's live.
